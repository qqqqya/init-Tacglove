# 05 按键单击、双击和长按修正记录

## 1. 本次确认的两个直接原因

### 1.1 生成代码读取了错误引脚

`glove_UMI_APP.ioc`中按键配置为PA11、上拉输入、低电平有效，但修改前的 `Core/Inc/main.h` 是：

```c
#define key_cap_Pin GPIO_PIN_1
#define key_cap_GPIO_Port GPIOA
```

这会让 `HAL_GPIO_ReadPin()`实际读取PA1，而不是PA11。状态机算法即使正确，也无法得到真实按键电平。

现已改为：

```c
#define key_cap_Pin GPIO_PIN_11
#define key_cap_GPIO_Port GPIOA
```

IOC本身已经是PA11，因此本次不修改IOC。以后重新生成CubeMX代码时仍需检查 `main.h` 与IOC是否一致。

### 1.2 “按下立即单击”会禁止另外两种手势

修改前 `KEY_SHORT_PRESS_ON_PRESS` 为1。按下消抖20 ms后立即产生单击，并把 `has_triggered` 置为true。后续长按判断要求 `has_triggered == false`，首次松开后进入双击窗口也要求尚未触发，因此长按和双击不可能成立。

现在已经删除“按下立即单击”分支，三种手势采用互斥判断：

- 按住达到400 ms：长按；
- 首次短按松开后，350 ms内完成第二次有效按下：双击；
- 首次短按松开后，350 ms内没有第二次按下：单击。

因为需要等待双击窗口，单击事件会比松开动作晚约350 ms，这是区分单击与双击必然产生的延迟。

## 2. 当前任务关系

工程仍只有 `key_task` 和 `led_task` 两个用户任务，没有使用Task Notification：

- `key_task`每1 ms调用 `bsp_key_handler_process()`；
- Handler只负责读取PA11、消抖、计时和锁存按键事件；
- `key_task`读取事件后，在switch中直接调用对应的LED任务接口；
- LED接口只记录待处理动作，耗时灯效和蜂鸣流程由 `led_task`执行；
- 因此LED闪烁和蜂鸣延时不会阻塞按键状态机继续扫描。

直接调用关系为：

```c
KEY_EVENT_SHORT_PRESS  -> led_task_on_short_press();
KEY_EVENT_LONG_PRESS   -> led_task_on_long_press();
KEY_EVENT_DOUBLE_CLICK -> led_task_on_double_click();
```

## 3. 当前验证反馈

- 单击：执行采集开始/停止逻辑；
- 长按：LED7相对稳定状态反转600 ms，并长鸣600 ms；
- 双击：LED7快速反转两次，并短鸣两次；
- 长按和双击反馈当前只用于确认识别结果，不改变待机/采集状态，后续业务含义确定后再替换。

## 4. 建议上板观察

1. 不按按键时，用万用表或逻辑分析仪确认PA11为高电平；
2. 按下时确认PA11持续为低电平；
3. 观察 `s_key.state` 是否依次进入消抖、按住、松开或等待双击状态；
4. 观察 `s_key.event` 是否只产生一个目标事件；
5. 分别测试单击、双击和超过400 ms的长按；
6. 若双击困难，只调整 `KEY_DOUBLE_CLICK_TIME_MS`，不要取消互斥判定流程。
