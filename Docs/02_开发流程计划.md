# 02 五指数采嵌入式软件完整开发计划

## 1. 最终目标与实施原则

当前开发工程是 `Tacapp_init`，先以单体固件完成硬件驱动和FreeRTOS板级验证。micro-ROS开始移植后再增加确有需要的业务目录；功能稳定后，最终整理为与参考项目 `Tacglove` 同类的正式产品结构：

> 当前进度：单体APP和阶段3通信已经验证，工程现已整理为 `Application` 与 `Bootloader` 两个可独立构建目录；SN及PC联调工具统一放在 `cmdfile`，升级工具在后续IAP小阶段继续加入该目录。

```text
Tacapp_init/
├── Bootloader/     启动、升级、校验、回滚、SN管理
├── Application/    FreeRTOS、BSP、业务状态机、micro-ROS Client
└── cmdfile/        PC端SN、micro-ROS联调、固件打包和升级工具
```

最终设备应具备以下完整能力：

- 六颗SK6805、数据采集按键和蜂鸣器稳定工作；
- MCU通过USART2/CH340直接运行micro-ROS Client；
- PC可通过ROS 2 topic与MCU进行publish/subscribe消息传输；
- MCU节点名和topic可由唯一SN派生，多设备互不冲突；
- `sn_tool.py`可读取SN、一次性写入SN、命令跳转APP和执行固件升级；
- Bootloader支持APP有效性检查、APP1/APP2备份与失败回滚；
- Application可被Bootloader正确跳转，升级前后外设、中断、FreeRTOS和micro-ROS均正常；
- 配置变更同步修改 `.ioc`、代码、构建脚本和编号文档。

实施顺序坚持“先稳定单体APP，再集成Bootloader”，避免同时调试板级驱动、RTOS、通信、Flash分区和加密升级。

## 2. 阶段1：板级基础与FreeRTOS骨架

### 2.1 阶段目标

建立可独立烧录、可重复验证的最小实时系统，确认新硬件的GPIO、电平、串联顺序和基础任务调度全部正确。

### 2.2 实施内容

1. 以当前CubeMX工程为唯一硬件配置源：
   - STM32G474RET6，系统主频170 MHz；
   - PB0配置为TIM3_CH3复用输出、Very High速度，驱动六颗SK6805；
   - TIM3_CH3使用DMA1_Channel1、Normal模式和Very High优先级输出PWM比较值；
   - PA11配置为上拉输入，按键低电平有效；
   - PB9配置为蜂鸣器输出，低电平有效；
   - USART1关闭；
   - USART2作为正式MCU-PC通道，RX使用Circular DMA，TX使用Normal DMA；
   - USART2及DMA中断抢占优先级设为6，以便后续安全调用FreeRTOS接口；
   - IWDG暂不启用，待Bootloader/IAP阶段统一设计喂狗与复位闭环。
2. 移植FreeRTOS V11.1.0：
   - GCC Cortex-M4F port；
   - `heap_4`动态内存；
   - FreeRTOS接管SVC、PendSV和SysTick；
   - 任务统一由 `task_manager_init()` 创建。
3. 建立当前最小目录：
   - `BSP`只处理硬件与逻辑映射；
   - `Tasks`当前只保留 `led_task`、`key_task` 和 `task_manager`；
   - key_task识别事件后直接调用led_task对外动作接口，不建立Application事件队列；
   - 两个 `xTaskCreate()` 都直接写在 `task_manager_init()` 中。
4. 完成首批功能：
   - 六灯RGB通道自检；
   - LED2~LED6绿色闪烁自检后绿色常亮待机；
   - 短按切换待机/采集演示状态：LED7蓝闪准备、蜂鸣后蓝色常亮，再次短按返回待机；
   - 长按和双击能够被独立识别，并通过LED7和蜂鸣器给出不同反馈；
   - 底层失败时六灯红色常亮。
5. 统一代码规范：
   - LED物理帧刷新统一命名为 `commit`；
   - LED Driver与Handler使用独立状态类型并显式转换；
   - 蜂鸣器只保留单一Driver，不额外建立Handler；
   - 主要接口、关键静态函数和硬件原因使用Doxygen注释。

### 2.3 交付物

- 可编译的单体开发固件源码；
- Debug/Release的ELF、HEX、BIN；
- 第一阶段移植与验证记录；
- PB0的TIM3_CH3 PWM DMA灯带波形测量记录。

### 2.4 验收标准

- 上电灯效、单击按键和蜂鸣器现象与定义一致；
- 逻辑分析仪确认每帧144 bit，T0H约0.3 us、T1H约0.9 us、码元约1.2 us、帧前后复位低电平各不少于300 us；
- Debug与Release均无编译错误和警告；
- 连续上电、快速重复按键和至少2小时运行无死机或无故切换。

### 2.5 当前状态

代码移植、编码规范、Debug/Release构建和上板现象均已通过，阶段1已关闭。GPIO+DWT历史方案已经被TIM3 PWM+DMA方案替换，原因和差异见 `07_GPIO_DWT与PWM_DMA方案对比.md`。

## 3. 阶段2：板级驱动稳定化与系统可观测性

### 3.1 阶段目标

把“能运行”的板级程序提升为“可长期运行、可定位故障、可作为通信开发底座”的板级固件。

### 3.2 已完成的稳定基线

1. 灯带已经由GPIO+DWT改为TIM3_CH3 PWM+DMA：
   - TIM3时钟170 MHz，PSC为0、ARR为203，码元周期1.2 us；
   - 逻辑0比较值51，T0H约0.3 us；逻辑1比较值153，T1H约0.9 us；
   - 六颗灯共144个数据码元，前后各256个零占空比码元；
   - 当前上板颜色、亮度、串联顺序和重复刷新均已稳定。
2. 按键已经确认为PA11，上拉输入、低电平有效：
   - 1 ms周期扫描；
   - 20 ms按下/松开消抖；
   - 400 ms长按门限；
   - 350 ms双击窗口；
   - 短按、长按、双击均已上板验证。
3. 蜂鸣器PB9高电平静音、低电平鸣叫，短按、长按和双击反馈可区分。
4. LED2~LED6固定对应相机1~5，LED7固定为系统状态灯；鱼眼相机不占用指示灯。
5. `.ioc`已经同步为PB0/TIM3_CH3/DMA1_Channel1，并保留USART2 RX/TX的DMA1_Channel2/3，三路DMA不存在通道占用冲突。

### 3.3 后续随阶段3继续记录的非阻塞项

- 记录Debug/Release最终实测波形截图和误差；
- 记录LED任务、按键任务以及新增micro-ROS任务的栈高水位；
- 记录FreeRTOS剩余heap和链接map中的Flash/RAM增量；
- 完成8小时灯效、按键和通信联合长稳测试；
- 3.3 V MCU直接驱动5 V SK6805 DIN目前可用，但仍属于硬件电平裕量风险，正式硬件继续评估AHCT类电平转换。

### 3.4 交付物

- 板级验证清单和实测数据；
- 任务栈与heap测量记录；
- 稳定的板级固件基线标签或版本号；
- 后续micro-ROS移植可复用的UART Driver接口。

### 3.5 验收标准

- Debug与Release波形都满足SK6805要求；
- 快速按压不重复触发，长按不会被识别为多次单击；
- 连续运行8小时无任务栈溢出、heap耗尽和异常灯色；
- 所有可失败接口返回分层错误码，新增代码符合 `C_CODE_STYLE_GUIDE.md`。

### 3.6 当前状态

阶段2的核心功能已经完成并稳定运行，允许进入阶段3。长稳时长、栈/heap高水位和最终波形截图作为阶段3联合回归的一部分继续补齐，不阻塞micro-ROS移植。

## 4. 阶段3：USART2 micro-ROS Client与ROS 2消息闭环

### 4.1 阶段目标

让STM32G474通过USART2/CH340直接成为micro-ROS Client，在不破坏现有本地按键、LED和蜂鸣器功能的前提下，完成“MCU状态上报、按键事件上报、六灯cmd下发、时间同步服务”的稳定闭环。

### 4.2 本阶段范围

本阶段包含：micro-ROS静态库、USART2 DMA传输、一个micro-ROS任务、连接/重连状态机、项目自定义msg/srv、PC端命令行验证节点和8小时通信测试。

本阶段不包含：相机READY/录制/落盘业务、Bootloader、IAP、SN写入工具、固件加密和正式量产状态机。阶段3最初使用 `mcu_dev`完成单板验证；进入阶段5后已经改为从SN派生设备标识，接口后缀保持不变。

### 4.3 参考工程的复用边界

| 项目 | 处理方式 | 原因 |
|---|---|---|
| micro-ROS头文件和 `libmicroros.a` | 直接复用参考产物已有类型支持；单独补入 `KeyState`、`LedCmd` 类型支持 | 保持MCUStatus和同步srv与参考工程一致，按本项目语义统一key_state名称 |
| `rmw_uros_set_custom_transport()`和USART2 DMA思路 | 复用结构，重写错误与超时处理 | 参考代码可作为骨架，但缺少完善的DMA溢出、串口错误和中断状态恢复 |
| `UNINIT/WAIT_AGENT/RUNNING/ERROR`连接状态机 | 复用思路 | 状态清晰，适合断线重建 |
| 断连或同步失败后直接 `NVIC_SystemReset()` | 不照搬 | 开发阶段应销毁ROS实体并重连，不能因为PC未启动就重启整机 |
| 参考 `DeviceCommand` 的单个 `led_mode/glove_led_mode` | 不照搬 | 无法准确表达本项目LED2~LED7六颗灯各自的颜色和闪烁状态 |
| ROS回调直接改全局LED/蜂鸣器变量 | 不照搬 | 回调只校验和投递命令，实际硬件仍由LED任务串行执行 |

### 4.4 初版ROS接口

节点名使用 `mcu_<device_id>`，topic/service前缀使用 `/mcu_<device_id>`。当前 `<device_id>` 来自Bootloader写入的SN，并把连字符转换为下划线；例如 `SN-TacGlove-000001`生成 `mcu_SN_TacGlove_000001`。SN无效时使用明确的 `mcu_SN_UNPROGRAMMED`，便于产测拦截。Domain ID沿用参考工程的9，PC端与MCU端必须一致。

| 方向 | 名称 | 类型 | QoS/触发 |
|---|---|---|---|
| MCU publish | `/mcu_<id>/key_state` | `common_msgs/msg/KeyState` | Reliable；短按、长按、双击确认后触发 |
| MCU publish | `/mcu_<id>/mcu_status` | `common_msgs/msg/MCUStatus` | Reliable；1 Hz心跳 |
| MCU subscribe | `/mcu_<id>/led_cmd` | `common_msgs/msg/LedCmd` | Reliable；PC下发六灯目标模式和蜂鸣器模式 |
| MCU service client | `/mcu_<id>/sync` | `common_msgs/srv/DeviceSynchronization` | 建立ROS实体后周期请求时间同步 |

六灯数组下标固定为：`[0]=LED2`、`[1]=LED3`、`[2]=LED4`、`[3]=LED5`、`[4]=LED6`、`[5]=LED7`。详细字段、枚举、方向和处理规则见 `08_阶段3_micro-ROS消息接口设计.md`。

### 4.5 任务与数据链路

阶段3只新增一个确有必要的 `micro_ros_task`，不提前创建相机或采集业务任务，也不新增空的 `Application` 目录。

```text
PA11 -> key_task -> 本地led_task动作接口 -> LED/蜂鸣器保持现有离线功能
                -> KeyState队列 -> micro_ros_task -> PC

PC -> LedCmd订阅回调 -> 单元素最新值Queue -> led_task -> LED BSP（PWM+DMA）/蜂鸣器Driver

FreeRTOS tick + LED业务状态 + 通信计数 -> MCUStatus -> micro_ros_task -> PC
```

- 所有 `rcl/rclc/rmw` 调用只允许在 `micro_ros_task` 中执行；
- key_task不直接调用 `rcl_publish()`，防止通信阻塞影响1 ms按键扫描；
- 订阅回调不直接刷新LED或驱动蜂鸣器，只完成六个灯模式和蜂鸣器模式校验后投递结构体；
- 使用FreeRTOS有界Queue传递带数据的事件和命令，不使用任务通知；
- 按键事件Queue满时丢弃当前ROS事件并累计内部drop计数，不回放过期事件；
- Agent未连接期间保留现有本地灯效，不回放已经过期的按键事件。

### 4.6 分步实施计划

#### 3A：冻结接口和PC端类型包

1. 在 `Interfaces/common_msgs` 提供 `KeyState.msg`、`MCUStatus.msg`、`LedCmd.msg` 和 `DeviceSynchronization.srv`。
2. `MCUStatus`和同步srv保持参考工程定义不变；`KeyState`保持原按键字段和枚举但采用与topic一致的名称；`LedCmd`固定为六元素灯模式数组和一个蜂鸣器模式字段。
3. PC端先执行 `colcon build`，再用 `ros2 interface show`确认字段和枚举。

完成标志：PC端能够导入全部类型，`ros2 interface show`与接口文档一致。

#### 3B：移植micro-ROS构建产物

1. 复制参考工程的micro-ROS静态库和include目录，复用 `MCUStatus`和同步srv的生成代码。
2. 为 `KeyState`和 `LedCmd`加入与生成器线格式相同的C结构和micro XRCE-DDS CDR类型支持；PC端以同一 `.msg` 生成ROS 2类型。
3. 在本工程CMake中加入头文件路径、静态库、所需源码和链接选项，不复制参考工程的业务Application代码。
4. 记录Debug/Release的Flash和RAM占用；上板后再用栈高水位收敛4096 words初始栈值。

完成标志：Debug/Release均可链接，类型支持符号完整，无未定义引用。

#### 3C：实现USART2 DMA custom transport

1. 保持当前 `.ioc`：PA2/PA3为USART2，RX=DMA1_Channel2 Circular，TX=DMA1_Channel3 Normal，中断优先级6。
2. RX持续DMA接收，依据NDTR维护环形读位置；正常回卷由2048字节环形缓存处理，串口错误或持续无响应由连接状态机销毁实体并重启transport。
3. TX使用DMA并设置有限超时，正确处理BUSY、ERROR和断连；禁止无限等待。
4. NDTR读取不关闭全局中断，避免破坏调用前的中断状态。
5. USART2字节流只承载micro-ROS XRCE-DDS；调试日志使用SWD/RTT或受控的其他通道。

完成标志：PC Agent可反复ping，串口拔插和Agent重启不会卡死UART或任务。

#### 3D：建立最小连接状态机

按 `UNINIT -> WAIT_AGENT -> CREATE_ENTITIES -> RUNNING -> DESTROY_ENTITIES -> WAIT_AGENT` 实现：

1. WAIT_AGENT以有限超时ping，不阻塞按键和LED任务；
2. CREATE_ENTITIES按allocator、support、node、publisher、subscription、service、executor顺序创建；
3. RUNNING周期 `spin_some`，发布心跳并检查Agent；
4. 连续ping失败后按创建顺序的逆序释放实体；
5. 重连采用退避，不复位MCU，不改变现有本地设备状态；
6. 每个已创建实体使用位图记录，保证部分创建失败时也能安全清理。

完成标志：启动顺序无论是“先MCU后Agent”还是“先Agent后MCU”都能自动连接，断开后可自动恢复。

#### 3E：接入按键publish

1. key_task识别短按、长按、双击后通过Task Notification触发本地反馈，同时向ROS Queue投递 `KeyState`事件；
2. Agent未连接或Queue满时丢弃ROS上报，不回放过期事件，也不影响本地动作；
3. 未完成时间同步时stamp置0，同步成功后填ROS时间；
4. PC测试节点打印并校验事件类型和时间戳。

完成标志：三类动作各测试100次，类型无混淆；断线时本地灯和蜂鸣器仍正常。

#### 3F：接入六灯subscribe和MCU状态publish

1. PC通过 `LedCmd.led_mode[6]` 分别设置LED2~LED7的灭、绿常亮/闪烁、红常亮、蓝常亮/闪烁；固定闪烁半周期为250 ms，并通过 `beep_mode`测试关闭、短鸣、长鸣和两次鸣叫。
2. 任一灯模式值大于5或蜂鸣器模式大于3时整条cmd拒绝；合法cmd覆盖写入单元素最新值Queue，避免拥塞后执行过期动作。
3. LED任务是远程灯光和蜂鸣器cmd的串行执行者，也是唯一执行LED BSP commit的任务；Agent断线后恢复本地灯状态并关闭远程蜂鸣器动作。
4. `MCUStatus`每秒上报固件版本、运行时间、公共系统状态以及收发计数；本阶段不发布LED状态，也不增加状态查询srv。

完成标志：PC可逐灯设置LED2~LED7并触发四种蜂鸣器模式，非法cmd不导致部分更新，`mcu_status`稳定1 Hz发布。

#### 3G：时间同步和联合回归

1. ROS实体建立后由MCU作为client周期请求 `DeviceSynchronization`；未启动PC server不阻断pub/sub和本地功能。
2. 验证USB热插拔、Agent停止/重启、错误消息、快速命令、按键与远端命令并发。
3. 记录任务栈高水位、最小heap、UART/DMA错误、publish/receive/drop/reconnect计数和Flash/RAM占用。
4. 进行8小时连续通信，并在期间周期操作按键和六灯。

完成标志：测试记录齐全，阶段3验收项全部通过。

### 4.7 交付物

- `Middleware/Micro-ROS`及USART2 DMA transport；
- micro-ROS管理任务和连接状态机；
- PC端状态监听与时间同步测试脚本；
- `common_msgs`的 `.msg/.srv`源文件及接口版本记录；
- 正式的MCU-PC接口定义文档；
- Agent启动、单设备测试和多设备测试说明。

### 4.8 验收标准

- PC Agent可稳定发现MCU节点；
- publish与subscribe双向连续运行8小时无不可恢复中断；
- 拔掉USB或停止Agent后MCU不死机，恢复连接后自动重建ROS实体；
- 短按、长按和双击能够正确发布，六灯cmd能稳定下发，MCU状态稳定上报；
- PC命令和物理按键最终都由同一个LED任务执行，ROS回调不直接操作BSP；
- 通信中断、超时和消息错误能被统计并映射到明确设备状态。

## 5. 阶段4：PC采集业务与相机状态联动

> 当前项目决定：相机通过USB Hub直接连接PC，暂不实施本阶段；阶段3通信验证通过后直接进入阶段5。本节保留为将来需要MCU参与相机业务联动时的设计储备。

### 5.1 阶段目标

建立MCU、PC采集程序和六路相机之间的可靠状态协议，使灯光表示“PC已经确认的真实状态”，而不是MCU单方面猜测。

### 5.2 实施内容

1. 定义统一设备状态机：
   - `BOOT_SELF_TEST`：LED2~LED6绿色闪烁；
   - `IDLE`：LED2~LED6绿色常亮，LED7熄灭；
   - `PREPARING`：LED7蓝色闪烁，等待PC和相机准备；
   - `CAPTURING`：蜂鸣确认后LED7蓝色常亮；
   - `STOPPING`：等待PC安全落盘；
   - `FAULT`：相关灯或全部灯红色常亮。
2. 建立命令/确认流程：
   - 按键只产生开始/停止意图；
   - MCU向PC发布请求并带Session ID和递增序号；
   - PC完成相机打开、预热和录制准备后回报READY；
   - MCU收到READY才鸣叫并进入CAPTURING；
   - 停止时PC完成文件落盘后回报STOPPED；
   - 超时、拒绝或故障进入FAULT并报告原因。
3. 建立相机灯映射：
   - LED2~LED6分别对应相机1~5；
   - 鱼眼相机不设置指示灯；
   - LED7只表示整体系统/采集状态；
   - 后续硬件结论变化时只修改Handler映射和文档。
4. 增强协议可靠性：
   - 心跳和通信超时；
   - 重复消息幂等；
   - 乱序或过期Session丢弃；
   - 数据丢包、相机掉线、磁盘写入失败等故障码；
   - MCU重启、PC重启和USB重连后的状态重新同步。
5. PC端形成可重复测试工具：
   - 虚拟相机/故障注入模式；
   - 自动发布命令并校验MCU反馈；
   - 保存消息时间线、Session和故障原因；
   - 实机多相机采集回归。

### 5.3 交付物

- MCU设备状态机和灯效策略；
- MCU-PC采集协议正式版；
- PC ROS 2控制/监测程序；
- 相机状态上报和故障注入测试；
- 端到端采集验证报告。

### 5.4 验收标准

- 相机未READY时LED7不会错误显示采集中；
- 每次采集都有唯一Session，开始、停止和落盘结果可追踪；
- 通信中断、数据丢包、单相机故障和PC异常退出均能进入预期状态；
- 恢复后可安全回到IDLE或由明确命令重新开始，不保留幽灵采集状态。

## 6. 阶段5：Bootloader、SNTool、IAP与正式工程交付

> 当前状态：阶段3的MCU publish与subscribe已由上板测试确认正常，阶段5已启动。具体实施和逐阶段验证记录见 `11_阶段5_Bootloader_SNTool_IAP实施记录.md`。

### 6.1 阶段目标

将已经稳定的单体Application整合为正式的 `Bootloader/Application/cmdfile` 产品工程，达到参考 `Tacglove` 的启动、SN、升级、回滚和micro-ROS能力，同时保留本板自己的外设配置与业务逻辑。

### 6.2 Flash布局与Application改造

在确认STM32G474RET6容量、双Bank边界和擦写粒度后，优先沿用参考布局：

| 区域 | 起始地址 | 大小 | 用途 |
|---|---:|---:|---|
| Bootloader | `0x08000000` | 64 KB | 启动、菜单、升级、校验、SN管理 |
| APP1 | `0x08010000` | 192 KB | 正式运行Application |
| APP2 | `0x08040000` | 192 KB | 升级前备份与失败回滚 |
| 配置/标志 | `0x08070000`以后 | 64 KB | SN、升级标志、版本与保留数据 |

具体工作：

- 修改Application链接脚本，使FLASH ORIGIN指向APP1、LENGTH限制为APP1大小；
- 启动早期设置VTOR到APP1向量表；
- 检查中断向量、FreeRTOS异常处理和HAL时基在跳转后正常；
- 把SN地址、升级标志地址、擦除页和Bank边界集中定义并静态校验；
- 确保Application的Flash占用不超过APP1，并为micro-ROS消息和后续功能保留裕量。

### 6.3 Bootloader功能

按可单独验证的顺序实现：

1. 最小安全跳转：
   - 检查APP1初始栈指针位于有效SRAM；
   - 检查Reset Handler位于APP1范围；
   - 关闭中断、SysTick、DMA和已启用外设；
   - 设置MSP与VTOR后跳转APP。
2. APP有效性与下载边界：
   - 当前先检查APP向量表，5.3增加长度、地址边界和CRC32；
   - Bootloader拒绝长度越界或校验失败的APP2镜像；
   - 固件头、版本及防降级规则留到5.5统一定义。
3. IAP接收：
   - USART2进入Bootloader菜单；
   - YMODEM先把明文固件接收到APP2；
   - 接收阶段不擦除或改写APP1；
   - 写入完成后校验APP2镜像，再标记为“可安装”。
4. APP安装与回滚：
   - 通过持久化升级状态记录安装进度；
   - APP2校验通过后再更新APP1，失败时恢复已验证的旧APP；
   - 掉电恢复必须依赖持久化升级状态，不依赖RAM变量；
   - 测试在擦除、备份、接收和写入各阶段断电。
5. 固件包安全：
   - 定义硬件型号、版本、长度、哈希或签名字段；
   - 区分固件加密与真实性/完整性验证；
   - 定义是否允许降级及密钥保护边界。
6. IWDG与启动闭环：
   - Bootloader长操作期间按经过审查的位置喂狗；
   - Application由健康监控统一喂狗；
   - 新APP首次启动成功后写入确认标志；
   - 连续启动失败时进入回滚或安全菜单。

### 6.4 SN与 `sn_tool.py`

以参考工具为兼容基线，保留并重新验证以下功能：

- SN格式：`SN-TacGlove-000000`，固定前缀加6位十进制序号；
- 读取命令：`*F_SN_R`；
- 写入握手命令：`#F_SN_W`；
- SN只允许写入一次，除非进入受控返修流程；
- PC菜单项 `3`发送字符 `1`跳转APP，菜单项 `4`发送字符 `2`进入固件下载；
- PC与Bootloader共享同一套16 bit状态码定义；
- SN写入后Application读取相同Flash地址，并用于micro-ROS节点/topic命名。

工具侧工作：

- 将串口号、波特率、超时和固件路径改为命令行参数，不在脚本中写死；
- 将固件加密、YMODEM传输、状态码解析和SN操作拆为可测试模块；
- 升级前校验固件头、目标硬件型号和版本；
- 输出结构化升级日志；
- 对错误串口、通信中断、非法SN、重复写入和错误固件给出明确提示。

### 6.5 加密、完整性与量产边界

- `encrypt_firmware.py`生成Bootloader能够解密的升级包；
- 明确“保密性”和“完整性/真实性”不是同一件事；若只使用对称加密和普通CRC，不能替代固件签名；
- 在量产前决定是否加入签名验证、防回滚计数和密钥保护；
- 调试阶段不启用不可逆RDP设置；完成恢复方案、产测和升级验证后再评估量产保护等级。

### 6.6 最终目录与构建交付

- `Application`：独立生成APP1 ELF/HEX/BIN及map文件；
- `Bootloader`：独立生成Bootloader ELF/HEX/BIN及map文件；
- `cmdfile`：统一放置 `sn_tool.py`、micro-ROS PC测试脚本以及后续加密/升级脚本；
- 根目录提供统一README、版本说明、Flash布局和端到端操作步骤；
- CI或本地脚本连续完成Debug/Release构建、大小检查和PC工具单元测试；
- 每次修改CubeMX配置时同步提交 `.ioc` 和生成代码差异说明。

### 6.8 阶段验收

1. 空片烧录Bootloader后可由 `sn_tool.py`写入并读取唯一SN。

3. 加密固件可经USART2/YMODEM升级；未加密、越界或校验错误固件会被拒绝。
4. 人为中断升级或制造错误镜像后可从APP2恢复，不会永久变砖。
5. 升级前后SN保持不变，micro-ROS节点/topic保持设备唯一性。
6. PC可持续订阅MCU状态并发布控制命令，USB断连后能够自动恢复。
7. 完成不少于20轮升级/回滚循环、8小时ROS通信和关键阶段断电测试。
