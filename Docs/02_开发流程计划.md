# 02 五指数采嵌入式软件完整开发计划

## 1. 最终目标与实施原则

当前开发工程是 `Tacapp_init`，先以单体固件完成硬件驱动和FreeRTOS板级验证。micro-ROS开始移植后再增加确有需要的业务目录；功能稳定后，最终整理为与参考项目 `Tacglove` 同类的正式产品结构：

```text
Tacapp_init/
├── AppEncrypt/     PC端SN、固件加密和升级工具
├── Bootloader/     启动、升级、校验、回滚、SN管理
└── Application/    FreeRTOS、BSP、业务状态机、micro-ROS Client
```

最终设备应具备以下完整能力：

- 六颗SK6805、数据采集按键和蜂鸣器稳定工作；
- MCU通过USART2/CH340直接运行micro-ROS Client；
- PC可通过ROS 2 topic与MCU进行publish/subscribe消息传输；
- MCU节点名和topic可由唯一SN派生，多设备互不冲突；
- `sn_tool.py`可读取SN、一次性写入SN、命令跳转APP和执行固件升级；
- Bootloader支持APP有效性检查、APP1/APP2备份与失败回滚；
- Application可被Bootloader正确跳转，升级前后外设、中断、FreeRTOS和micro-ROS均正常；
- 配置变更同步修改 `.ioc`、代码、构建脚本和编号文档。

实施顺序坚持“先稳定单体APP，再集成Bootloader”，避免同时调试板级驱动、RTOS、通信、Flash分区和加密升级。

## 2. 阶段1：板级基础与FreeRTOS骨架

### 2.1 阶段目标

建立可独立烧录、可重复验证的最小实时系统，确认新硬件的GPIO、电平、串联顺序和基础任务调度全部正确。

### 2.2 实施内容

1. 以当前CubeMX工程为唯一硬件配置源：
   - STM32G474RET6，系统主频170 MHz；
   - PB0配置为Very High输出，驱动六颗SK6805；
   - PA11配置为上拉输入，按键低电平有效；
   - PB9配置为蜂鸣器输出，低电平有效；
   - USART1关闭；
   - USART2作为正式MCU-PC通道，RX使用Circular DMA，TX使用Normal DMA；
   - USART2及DMA中断抢占优先级设为6，以便后续安全调用FreeRTOS接口；
   - TIM3与IWDG暂不启用。
2. 移植FreeRTOS V11.1.0：
   - GCC Cortex-M4F port；
   - `heap_4`动态内存；
   - FreeRTOS接管SVC、PendSV和SysTick；
   - 任务统一由 `task_manager_init()` 创建。
3. 建立当前最小目录：
   - `BSP`只处理硬件与逻辑映射；
   - `Tasks`当前只保留 `led_task`、`key_task` 和 `task_manager`；
   - 按键通过FreeRTOS任务通知直接唤醒LED任务，不建立Application事件队列；
   - 两个 `xTaskCreate()` 都直接写在 `task_manager_init()` 中。
4. 完成首批功能：
   - 六灯RGB通道自检；
   - LED2~LED6绿色闪烁自检后绿色常亮待机；
   - 每次单击按键后LED7蓝闪、蜂鸣器短鸣；
   - 动作结束后LED7熄灭并返回待机；
   - 底层失败时六灯红色常亮。
5. 统一代码规范：
   - LED物理帧刷新统一命名为 `commit`；
   - LED Driver与Handler使用独立状态类型并显式转换；
   - 蜂鸣器只保留单一Driver，不额外建立Handler；
   - 主要接口、关键静态函数和硬件原因使用Doxygen注释。

### 2.3 交付物

- 可编译的单体开发固件源码；
- Debug/Release的ELF、HEX、BIN；
- 第一阶段移植与验证记录；
- PB0灯带波形测量记录。

### 2.4 验收标准

- 上电灯效、单击按键和蜂鸣器现象与定义一致；
- 逻辑分析仪确认每帧144 bit，T0H约0.3 us、T1H约0.9 us、码元约1.2 us、复位低电平不少于200 us；
- Debug与Release均无编译错误和警告；
- 连续上电、快速重复按键和至少2小时运行无死机或无故切换。

### 2.5 当前状态

代码移植和上板现象已经通过；编码规范已统一。仍需把Debug与Release波形实测值记录到验证文档，阶段1才正式关闭。

## 3. 阶段2：板级驱动稳定化与系统可观测性

### 3.1 阶段目标

把“能运行”的板级程序提升为“可长期运行、可定位故障、可作为通信开发底座”的板级固件。

### 3.2 实施内容

1. 稳定灯带时序：
   - 分别测量Debug和Release波形；
   - 若有偏差，只修改LED Driver的时序实现，不改变Handler映射和灯效任务；
   - 测试USB插拔、按键中断活动及任务切换期间的帧完整性；
   - 记录3.3 V GPIO直驱5 V SK6805属于当前已验证可用但存在电平裕量风险的硬件决定。
2. 稳定按键输入：
   - 验证PA11空闲高、按下低；
   - 测试短按、长按、连按和机械抖动；
   - 当前只产生单击事件，长按/双击预留但不实现。
3. 稳定蜂鸣器输出：
   - 验证PB9高电平静音、低电平鸣叫；
   - 确认120 ms提示音在批次差异下可辨识；
   - 鸣叫节奏保留在Task，GPIO有效电平只存在于Driver。
4. 增加可观测性：
   - 统计FreeRTOS剩余heap；
   - 检查各任务最小剩余栈；
   - 记录启动原因、关键错误码和通信计数的接口；
   - 预留日志后端，但在SK6805时序临界区和ISR内不打印。
5. 建立回归检查：
   - `.ioc`关键项核对表；
   - Debug/Release构建；
   - 上电、按键、灯效、蜂鸣器测试；
   - Flash/RAM占用记录。

### 3.3 交付物

- 板级验证清单和实测数据；
- 任务栈与heap测量记录；
- 稳定的板级固件基线标签或版本号；
- 后续micro-ROS移植可复用的UART Driver接口。

### 3.4 验收标准

- Debug与Release波形都满足SK6805要求；
- 快速按压不重复触发，长按不会被识别为多次单击；
- 连续运行8小时无任务栈溢出、heap耗尽和异常灯色；
- 所有可失败接口返回分层错误码，新增代码符合 `C_CODE_STYLE_GUIDE.md`。

## 4. 阶段3：USART2 micro-ROS Client与ROS 2消息闭环

### 4.1 阶段目标

让STM32G474通过USART2/CH340直接成为micro-ROS Client，在PC端micro-ROS Agent和ROS 2环境中实现稳定、可重连的publish/subscribe。

### 4.2 实施内容

1. 移植参考工程的micro-ROS Jazzy构建产物与适配层：
   - micro-ROS头文件和 `libmicroros.a`；
   - allocator适配；
   - MCU时间源；
   - USART2 DMA custom transport；
   - 所需标准消息与 `common_msgs` 类型支持。
2. 完成USART2传输层：
   - RX DMA持续循环接收，软件维护读位置；
   - TX DMA发送并处理busy、完成和超时；
   - DMA缓冲区溢出、串口错误和重新启动有明确状态；
   - micro-ROS和调试日志不能无协议地混用同一USART2字节流。
3. 建立micro-ROS连接状态机：
   - 等待Agent；
   - ping成功后创建support、node、publisher、subscription和executor；
   - 周期spin与时间同步；
   - Agent断开后按逆序销毁实体并重连；
   - 通信状态通过明确接口通知LED任务，不直接在micro-ROS回调中编排灯效；业务扩大后再决定是否建立Application状态层。
4. 先做最小标准消息闭环，再引入项目消息：
   - MCU周期发布心跳、固件版本、运行时间和当前状态；
   - MCU发布物理按键单击事件；
   - MCU订阅PC开始采集、停止采集和状态控制命令；
   - PC脚本验证命令和反馈的序号、时间戳及内容。
5. 接入SN派生名称：
   - 未烧录SN时使用明确的 `NO-SN` 限制模式，不允许伪装为正式设备；
   - 已烧录SN时生成唯一node名和topic前缀；
   - 参考工程Domain ID为9，是否沿用应在接口冻结时确认；
   - 多设备并联时验证节点和topic不会冲突。

### 4.3 初版ROS接口方向

参考工程使用以下SN隔离形式，最终名称和字段在本阶段冻结：

| 方向 | 建议用途 | 参考命名形式 |
|---|---|---|
| MCU publish | 按键/设备侧事件 | `/mcu_<SN>/button_device_state` |
| MCU publish | 远端控制反馈 | `/mcu_<SN>/button_remote_ctrl` |
| MCU publish | MCU心跳和状态 | `/mcu_<SN>/mcu_status` |
| MCU subscribe | PC设备控制命令 | `/mcu_<SN>/command` |

必须进一步定义：消息字段、QoS、发布周期、命令确认、序列号、超时、重复命令幂等和版本兼容策略。

### 4.4 交付物

- `Middleware/Micro-ROS`及USART2 DMA transport；
- micro-ROS管理任务和连接状态机；
- ROS 2 publish/subscribe测试脚本；
- 正式的MCU-PC接口定义文档；
- Agent启动、单设备测试和多设备测试说明。

### 4.5 验收标准

- PC Agent可稳定发现MCU节点；
- publish与subscribe双向连续运行8小时无不可恢复中断；
- 拔掉USB或停止Agent后MCU不死机，恢复连接后自动重建ROS实体；
- PC命令和物理按键进入同一状态处理接口；
- 通信中断、超时和消息错误能被统计并映射到明确设备状态。

## 5. 阶段4：PC采集业务与相机状态联动

### 5.1 阶段目标

建立MCU、PC采集程序和六路相机之间的可靠状态协议，使灯光表示“PC已经确认的真实状态”，而不是MCU单方面猜测。

### 5.2 实施内容

1. 定义统一设备状态机：
   - `BOOT_SELF_TEST`：LED2~LED6绿色闪烁；
   - `IDLE`：LED2~LED6绿色常亮，LED7熄灭；
   - `PREPARING`：LED7蓝色闪烁，等待PC和相机准备；
   - `CAPTURING`：蜂鸣确认后LED7蓝色常亮；
   - `STOPPING`：等待PC安全落盘；
   - `FAULT`：相关灯或全部灯红色常亮。
2. 建立命令/确认流程：
   - 按键只产生开始/停止意图；
   - MCU向PC发布请求并带Session ID和递增序号；
   - PC完成相机打开、预热和录制准备后回报READY；
   - MCU收到READY才鸣叫并进入CAPTURING；
   - 停止时PC完成文件落盘后回报STOPPED；
   - 超时、拒绝或故障进入FAULT并报告原因。
3. 建立相机灯映射：
   - LED2~LED6分别对应相机1~5；
   - 鱼眼相机不设置指示灯；
   - LED7只表示整体系统/采集状态；
   - 后续硬件结论变化时只修改Handler映射和文档。
4. 增强协议可靠性：
   - 心跳和通信超时；
   - 重复消息幂等；
   - 乱序或过期Session丢弃；
   - 数据丢包、相机掉线、磁盘写入失败等故障码；
   - MCU重启、PC重启和USB重连后的状态重新同步。
5. PC端形成可重复测试工具：
   - 虚拟相机/故障注入模式；
   - 自动发布命令并校验MCU反馈；
   - 保存消息时间线、Session和故障原因；
   - 实机多相机采集回归。

### 5.3 交付物

- MCU设备状态机和灯效策略；
- MCU-PC采集协议正式版；
- PC ROS 2控制/监测程序；
- 相机状态上报和故障注入测试；
- 端到端采集验证报告。

### 5.4 验收标准

- 相机未READY时LED7不会错误显示采集中；
- 每次采集都有唯一Session，开始、停止和落盘结果可追踪；
- 通信中断、数据丢包、单相机故障和PC异常退出均能进入预期状态；
- 恢复后可安全回到IDLE或由明确命令重新开始，不保留幽灵采集状态。

## 6. 阶段5：Bootloader、SNTool、IAP与正式工程交付

### 6.1 阶段目标

将已经稳定的单体Application整合为正式的 `Bootloader/Application/AppEncrypt` 产品工程，达到参考 `Tacglove` 的启动、SN、升级、回滚和micro-ROS能力，同时保留本板自己的外设配置与业务逻辑。

### 6.2 Flash布局与Application改造

在确认STM32G474RET6容量、双Bank边界和擦写粒度后，优先沿用参考布局：

| 区域 | 起始地址 | 大小 | 用途 |
|---|---:|---:|---|
| Bootloader | `0x08000000` | 64 KB | 启动、菜单、升级、校验、SN管理 |
| APP1 | `0x08010000` | 192 KB | 正式运行Application |
| APP2 | `0x08040000` | 192 KB | 升级前备份与失败回滚 |
| 配置/标志 | `0x08070000`以后 | 64 KB | SN、升级标志、版本与保留数据 |

具体工作：

- 修改Application链接脚本，使FLASH ORIGIN指向APP1、LENGTH限制为APP1大小；
- 启动早期设置VTOR到APP1向量表；
- 检查中断向量、FreeRTOS异常处理和HAL时基在跳转后正常；
- 把SN地址、升级标志地址、擦除页和Bank边界集中定义并静态校验；
- 确保Application的Flash占用不超过APP1，并为micro-ROS消息和后续功能保留裕量。

### 6.3 Bootloader功能

按可单独验证的顺序实现：

1. 最小安全跳转：
   - 检查APP1初始栈指针位于有效SRAM；
   - 检查Reset Handler位于APP1范围；
   - 关闭中断、SysTick、DMA和已启用外设；
   - 设置MSP与VTOR后跳转APP。
2. APP有效性与版本：
   - 固件头包含魔数、长度、版本、校验值和构建信息；
   - Bootloader拒绝长度越界或校验失败的APP；
   - 定义是否允许降级及版本比较规则。
3. IAP升级：
   - USART2进入Bootloader菜单；
   - YMODEM接收加密固件；
   - 擦除APP1并分块写入；
   - 写入完成后校验固件，再标记可启动。
4. APP1/APP2回滚：
   - 升级前验证APP1并备份到APP2；
   - 新APP下载、解密、写入或校验失败时恢复APP2；
   - 掉电恢复必须依赖持久化升级状态，不依赖RAM变量；
   - 测试在擦除、备份、接收和写入各阶段断电。
5. IWDG与启动闭环：
   - Bootloader长操作期间按经过审查的位置喂狗；
   - Application由健康监控统一喂狗；
   - 新APP首次启动成功后写入确认标志；
   - 连续启动失败时进入回滚或安全菜单。

### 6.4 SN与 `sn_tool.py`

以参考工具为兼容基线，保留并重新验证以下功能：

- SN格式：`SN-YYYYMMDD-XXXXXX`；
- 读取命令：`*F_SN_R`；
- 写入握手命令：`#F_SN_W`；
- SN只允许写入一次，除非进入受控返修流程；
- 菜单命令 `1` 跳转APP，命令 `2` 进入固件下载；
- PC与Bootloader共享同一套16 bit状态码定义；
- SN写入后Application读取相同Flash地址，并用于micro-ROS节点/topic命名。

工具侧工作：

- 将串口号、波特率、超时和固件路径改为命令行参数，不在脚本中写死；
- 将固件加密、YMODEM传输、状态码解析和SN操作拆为可测试模块；
- 升级前校验固件头、目标硬件型号和版本；
- 输出结构化升级日志；
- 对错误串口、通信中断、非法SN、重复写入和错误固件给出明确提示。

### 6.5 加密、完整性与量产边界

- `encrypt_firmware.py`生成Bootloader能够解密的升级包；
- 明确“保密性”和“完整性/真实性”不是同一件事；若只使用对称加密和普通CRC，不能替代固件签名；
- 在量产前决定是否加入签名验证、防回滚计数和密钥保护；
- 调试阶段不启用不可逆RDP设置；完成恢复方案、产测和升级验证后再评估量产保护等级。

### 6.6 最终目录与构建交付

- `Application`：独立生成APP1 ELF/HEX/BIN及map文件；
- `Bootloader`：独立生成Bootloader ELF/HEX/BIN及map文件；
- `AppEncrypt`：提供依赖说明、加密、SN和升级脚本；
- 根目录提供统一README、版本说明、Flash布局和端到端操作步骤；
- CI或本地脚本连续完成Debug/Release构建、大小检查和PC工具单元测试；
- 每次修改CubeMX配置时同步提交 `.ioc` 和生成代码差异说明。

### 6.7 阶段验收

1. 空片烧录Bootloader后可由 `sn_tool.py`写入并读取唯一SN。
2. Bootloader可跳转APP1，Application灯效、按键、FreeRTOS和micro-ROS均正常。
3. 加密固件可经USART2/YMODEM升级；未加密、越界或校验错误固件会被拒绝。
4. 人为中断升级或制造错误镜像后可从APP2恢复，不会永久变砖。
5. 升级前后SN保持不变，micro-ROS节点/topic保持设备唯一性。
6. PC可持续订阅MCU状态并发布控制命令，USB断连后能够自动恢复。
7. 完成不少于20轮升级/回滚循环、8小时ROS通信和关键阶段断电测试。

| M3 ROS通信闭环 | M2完成 | USART2双向pub/sub、SN命名和自动重连通过 |
| M4 相机业务闭环 | M3完成 | READY/CAPTURING/STOPPED/FAULT端到端通过 |
| M5 正式产品工程 | M4完成 | Boot/App/SNTool/IAP/回滚及量产验证通过 |

任何阶段没有完成验收证据时，不把后续阶段的现象当作前一阶段已经可靠。例如micro-ROS能够偶尔通信，不代表USART2 DMA重连已经完成；Bootloader能够跳转一次，也不代表掉电回滚已经完成。
